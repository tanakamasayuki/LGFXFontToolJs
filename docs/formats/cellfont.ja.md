# CellFont — ビットマップフォント形式 仕様

[English](./cellfont.en.md)

- 対象読者: この形式の生成器・描画器を実装する人
- 状態: **v1（確定）**  `CELLFONT_SPEC_VERSION == 1`
- 最終更新: 2026-08-28

## 0. 位置づけ

CellFont は、フラッシュが 16〜64 KB 級のマイコンにビットマップフォントを載せるための形式。
デコーダが小さく、収録文字の増減が安く済むことを狙う。

本書は**生成器と描画器の間の取り決めだけ**を定める。両者は別の実装者でよく、
本書だけを読めば双方を実装できる。特定のライブラリやツールには依存しない。

主な対象は **1bpp・墨面の高さ 16px 以下のピクセルグリッドフォント**で、
そこでデータがいちばん密になる。**より大きなサイズでも使えるし、収録字数が少なければ
総量で有利なことも多い**（§12）。

**CellFont はコンパイル時形式である。** データは C ソースとしてファームウェアに焼き込まれ、
実行時に読み込む容器は定義しない（§11）。将来容器を定義する場合に備えて
magic `CEL1` だけを予約する。

名前は「全グリフが 1 つの**セル**を共有し、字ごとに持つのは変わるものだけ」から。
エンコーダ規範（§9）もこの語で説明できる。

## 1. 設計目標

1. **選択は実行時ではなく生成時に済ませ、結果をデータで表す。**
   描画器は分岐を辿るだけでよく、探索も走査もしない。
2. **収録文字の増減が安い。** 1 字足したときの増分が、その 1 字の実費に比例すること。
   範囲が飛んだだけで桁が変わる形式は使えない（§10）。
3. **描画器が小さい。** 表現力よりデコーダのバイト数を優先する。
   圧縮を持たないのはこのため（§12.2）。

## 2. 中心の考え方

決めることは 3 つ。どれも **ポインタが `NULL` かどうか**で表す。

| 選択 | `NULL` のとき | 非 `NULL` のとき |
| --- | --- | --- |
| `codes`（索引） | **連続** — `first` から `count` 個 | **疎** — コード表を二分探索 |
| `glyphs`（グリフ表） | **固定ピッチ** — 全グリフ共通の幅・送り幅 | **可変ピッチ** — 4 バイト/字 |
| `next`（連鎖） | **終端** | この表に無ければ次のフォントを見る |

**グリフごとに持つのは「変わるもの」だけ。**
高さ・`xOffset`・`yOffset` は全グリフ共通で、これが per-glyph bbox を持つ形式との一番の差。
共通なので ascent が定数になり、フォント設定時に全グリフを走査する必要がない。

組み合わせすべてを 1 つのデコーダが扱う。分岐は各 1 か所。

## 3. 構造

```c
typedef struct CellGlyph {   /* 可変ピッチのときだけ。4 バイト固定 */
  uint16_t offset;             /* bitmap 先頭からのバイトオフセット */
  uint8_t  width;              /* グリフの幅（画素）。0 も合法（§4） */
  uint8_t  xAdvance;           /* 送り幅（画素） */
} CellGlyph;

typedef struct CellFont {
  const uint8_t*         bitmap;      /* グリフのビット列 */
  const CellGlyph*       glyphs;      /* NULL = 固定ピッチ */
  const uint16_t*        codes;       /* NULL = 連続索引。長さ count - headCount */
  const struct CellFont* next;        /* NULL = 連鎖の終端 */
  uint16_t first;                     /* 連続索引の先頭 / 疎索引では頭ブロックの先頭 */
  uint16_t count;                     /* 収録グリフ数 */
  uint8_t  width, height;             /* width は固定ピッチ用。height は全グリフ共通 */
  uint8_t  xAdvance, yAdvance;        /* xAdvance は固定ピッチ用。yAdvance は行送り */
  int8_t   xOffset, yOffset;          /* 全グリフ共通 */
  uint8_t  bytesPerGlyph;             /* 固定ピッチ用。実行時に除算しないため */
  uint8_t  headCount;                 /* 疎索引の頭ブロック長。0 = 頭なし */
} CellFont;
```

ヘッダは **28 バイト**（32bit ポインタ）、**20 バイト**（16bit ポインタ）。

`bytesPerGlyph` は固定ピッチのとき `ceil(width * height / 8)` に等しい。
実行時に掛け算・割り算をしないために持つ。

`headCount` はアライメントの余りに収まるので、**この 1 バイトでヘッダは増えない。**

`CellGlyph` は 4 バイト・アライメント 2。`CellFont` はポインタが 32bit のとき
アライメント 4 で、末尾に余りが無い。

**未使用のフィールドには必ず 0 を入れる。** 決定性（§9.4）のために必要。

| 状況 | 0 にするフィールド |
| --- | --- |
| 固定ピッチ（`glyphs == NULL`） | なし |
| 可変ピッチ | `width`, `xAdvance`, `bytesPerGlyph` |
| 連続索引（`codes == NULL`） | `headCount` |
| 疎索引で頭ブロックが無い | `first`, `headCount` |

## 4. ビットマップの並び

**1bpp 専用。ビットが 1 の画素が墨。** 行は上から下へ、各行は左から右へ MSB first。
行を連結したビット列で、**行の途中ではバイト境界に揃えない。
グリフの先頭だけがバイト境界に揃う。**

1 グリフのバイト数は `ceil(width * height / 8)`。

- **固定ピッチ**: グリフ `n` の先頭は `bitmap + n * bytesPerGlyph`。表を引かない
- **可変ピッチ**: グリフ `n` の先頭は `bitmap + glyphs[n].offset`

グリフの高さは常に `height`、描画位置は常に `xOffset` / `yOffset`。
つまり**すべてのグリフが同じ高さの箱に入っている。**

**幅が 0 のグリフは合法。** 空白は実際のフォントでは墨面を持たない
（調べた範囲のすべてのフォントで `0x0` + 非ゼロの送り幅）。

- 可変ピッチでは `width = 0` とし、ビットマップを 1 バイトも消費しない。
  その `offset` は次のグリフの `offset` と同値でよい
- 固定ピッチでは全グリフが `width` 幅なので、空白は**空のセル**（すべて 0 のビット列）になる。
  §9.1 のセル規則が自動的にそうする

**`width` が `xAdvance` を超えてよい**（張り出し）。描画は `width` 列ぶん、
ペンの前進は `xAdvance` ぶん。

この並びは GFXfont と同じなので、既存の GFXfont 資産はビットマップをそのまま流用でき、
組み替えるのはメタデータだけで済む。

## 5. グリフの並び順

ビットマップ・グリフ表は次の順に並ぶ。**コード表もこの順に対応する。**

1. **頭ブロック** — `first` から `headCount` 個の連続したコード（`codes` には現れない）
2. **しっぽ** — 残りのコードを**昇順**に。`codes[0 .. count-headCount-1]` が対応する

連続索引（`codes == NULL`）のときは頭ブロックだけで、`headCount` は使わない。

**`codes` は狭義単調増加でなければならない**（重複禁止）。二分探索の前提であり、
破ると静かに別のグリフが出る。頭ブロックのコードは `codes` に現れない。

## 6. 索引

コード `c` からグリフ番号を引く手順。

```c
int cellFontIndex(const CellFont* f, uint16_t c) {
  if (f->codes == NULL) {                       /* 連続 */
    if (c < f->first || c >= f->first + f->count) return -1;
    return c - f->first;
  }
  if (f->headCount && c >= f->first && c < f->first + f->headCount) {
    return c - f->first;                        /* 疎・頭ブロック */
  }
  uint16_t lo = 0, hi = f->count - f->headCount;   /* 疎・しっぽ */
  while (lo < hi) {
    uint16_t mid = (lo + hi) >> 1;
    uint16_t v = f->codes[mid];
    if (v == c) return f->headCount + mid;
    if (v < c) lo = mid + 1; else hi = mid;
  }
  return -1;
}
```

見つからなければ `f->next` を辿る。

**連鎖のどれにも無かったとき（未収録）の扱いは次のとおり。**

1. 連鎖のいずれかに **U+FFFD** があれば、そのグリフを描く
2. 無ければ**何も描かず、ペンを進めない**（送り幅 0）

形式にフォールバック用のメトリクスを持たせない。豆腐を出すかどうかは
「文字集合に U+FFFD を入れるか」という**生成時の選択**になり、結果はデータに現れる（§1 目標 1）。
描画器が独自の既定を持つと同じフォントが実装ごとに違って見えるので、ここは規範とする。

**頭ブロックを持つ理由。** 現実の文字集合は「ASCII 全部 + 記号数個」という形になる。
全体を疎にすると、連続している ASCII 95 字にも 2 バイト/字のコード表が付く。
頭を切り出すとそこが丸ごと消える。

| | 全体を疎 | 頭 + しっぽ | 削減 |
| --- | --- | --- | --- |
| 4x8 ASCII 95 字 + 記号 6 字 | 990 B | **800 B** | −19.2% |
| 6x12 ASCII 95 字 + 記号 6 字 | 1,442 B | **1,252 B** | −13.2% |

## 7. 連鎖（`next`）

`next` を辿る順に探し、**最初に見つかったフォントが勝つ。**
生成器は収録集合が重ならないように出す。

連鎖する各フォントは `height` / `xOffset` / `yOffset` を別々に持ってよい
（幅の違うグリフ群は墨面の高さも違う）。
ただし **`yAdvance` は連鎖全体で一致していなければならない。**
行送りが揃わないと段組みが壊れる。先頭のフォントの `yAdvance` を正とする。

連鎖が要る理由は §9.2 と §10。**`next` を描画器の API（フォントの配列）ではなく
構造体に置くのは、連鎖が §1 の目標 2 を成立させている仕組みだからである。**
API に置くと、生成したヘッダが描画器ごとに違う繋ぎ方を要求することになり、
可搬でなくなる。代償はフォント 1 本あたり 4 バイト（16bit ポインタなら 2 バイト）で、
連鎖が生む削減（8px の日本語 190 字で 690 B）に対して 1% 程度。

## 8. データ量

グリフ 1 字のビットマップを b バイト、グリフ数を n、頭ブロック長を h とすると:

| 形式 | データ量 |
| --- | --- |
| 固定ピッチ・連続 | 28 + n·b |
| 固定ピッチ・頭 + 疎 | 28 + n·b + 2(n−h) |
| 固定ピッチ・疎 | 28 + n·(b+2) |
| 可変ピッチ・連続 | 28 + n·(b+4) |
| 可変ピッチ・頭 + 疎 | 28 + n·(b+4) + 2(n−h) |
| 可変ピッチ・疎 | 28 + n·(b+6) |

参考として GFXfont は `12 + n·b + 7·span`。`span` は `first`〜`last` の**範囲**であって
グリフ数ではない。U+4E00〜U+9FA5 に散った 500 字を収めるには 20,902 件のグリフ表
（**146 KB**）が要る。**疎索引が桁違いに効くのはここ。**

## 9. エンコーダ規範

同じ入力から常に同じデータが出るために、生成器は次に従う。

### 9.1 刈り込まず、セルで出す

`width` には**墨面の幅ではなくセル幅（`xAdvance` 以上の値）を入れる。**

刈り込むと `i` と `W` で幅が変わり、固定ピッチ判定が落ちて 4 バイト/字のグリフ表が付く。
セルで出すと詰め物のぶんビットマップは増えるが、**表が丸ごと消えるほうが大きい。**

| 4x8 の ASCII 95 字 | 刈り込み | セル |
| --- | --- | --- |
| データ量 | 可変ピッチ 726 B | **固定ピッチ 408 B** |

**ただし大きいフォントでは逆転する**（詰め物が表より高くつく）。
生成器は**両方を計算して小さいほうを採る。**

### 9.2 セル幅クラスで分け、`next` でつなぐ

幅の違うグリフが混ざったフォントは、**1 本にまとめると固定ピッチ判定がまず通らない。**
`(width, xAdvance)` が同じものごとに分けて連鎖すると、各フォントが固定ピッチになり
グリフ表が消える。

| 190 字（ASCII 95 + 全角 95） | 連鎖 | 単一 | クラス数 |
| --- | --- | --- | --- |
| 4x8 / 8x9 | **1,473 B** | 2,163 B | 2 |
| 6x12 / 12x11 | **2,708 B** | 3,245 B | 2 |
| 8x16 / 16x16 | **4,798 B** | 4,924 B | 2 |
| 12x24 / 24x22 | **9,257 B** | 9,972 B | 2 |
| 20x40 / 40x38 | **24,700 B** | 25,958 B | 2 |

**小さいフォントほど効く。** クラス数が多い書体（比例欧文など）では分けても得にならないので、
生成器は**両方を計算して小さいほうを採る。**

クラスごとに分けたとき、各フォントは固定ピッチになる:

| | CellFont | 参考: u8g2 |
| --- | --- | --- |
| 4x8 固定・連続 95 字 | **408 B** | 764 B |
| 8x9 固定・頭+疎 95 字 | **1,065 B** | 1,390 B |
| 8x16 固定・連続 95 字 | 1,548 B | **1,282 B** |
| 16x16 固定・頭+疎 95 字 | 3,250 B | **3,100 B** |

### 9.3 索引とグリフ表の選択

利用者に選ばせない。**入力を見て小さいほうを選ぶ。**

| 判定 | 結果 |
| --- | --- |
| 全グリフの `width` と `xAdvance` が同一 | `glyphs = NULL`、`bytesPerGlyph` を設定 |
| 収録コードが連続 | `codes = NULL`、`headCount = 0` |
| 疎で、最長の連続並びが 2 以上 | その並びを頭ブロックにする（`first` = その先頭） |
| 疎で連続並びが無い | `headCount = 0`、`codes` に全コード |

頭ブロックが 255 を超えるときは 255 で打ち切る。残りはしっぽに入り、正しく動く。

### 9.4 正準出力

**同じ入力からはバイト一致の出力が出ること。**

- コードポイントを昇順にソートしてから並べる（入力の順序に依存しない）
- 出力にタイムスタンプ・絶対パス・ホスト名・生成器のバージョンを含めない
- 16 進の桁数・1 行あたりのバイト数・改行・末尾改行を固定する
- 浮動小数を出力に出さない

## 10. 収録文字の増減

**この形式のいちばん重要な性質。** 4x8 の ASCII 95 字から文字を足したときの増分:

| 文字集合 | n | CellFont | Δ | 参考: GFXfont | Δ | 参考: u8g2 | Δ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ASCII 95 字 | 95 | 408 | — | 889 | — | 764 | — |
| +1 字 | 96 | **437** | **+29** | 1,240 | +351 | 780 | +16 |
| +5 字 | 100 | **477** | **+40** | 60,180 | **+58,940** | 822 | +42 |
| +10 字 | 105 | **528** | **+51** | 87,806 | +27,626 | 864 | +42 |
| +20 字 | 115 | **648** | **+120** | 247,696 | +159,890 | 1,038 | +174 |
| +30 字 | 125 | **758** | **+110** | 271,430 | +23,734 | 1,195 | +157 |

GFXfont は範囲が飛んだ瞬間に桁が変わる（1 字足すのに 58,940 バイト）。
CellFont は疎索引と連鎖によって、増分が**その字の実費に比例する。**

この性質を成立させているのは 3 つ。

1. **疎索引**（§2）— 収録コードが飛んでいても表は 2 バイト/字
2. **頭ブロック**（§6）— 連続部分にはコード表が付かない
3. **セル幅クラスでの連鎖**（§9.2）— 幅の違う字を足しても、既存のフォントは固定ピッチのまま

3 が無いと、ASCII だけのフォントに幅の違う字を 1 つ足しただけで固定ピッチ判定が落ち、
全グリフに 4 バイトの表が付いて **+394 バイト**になる。連鎖があれば **+29 バイト**。

## 11. C ソース出力

CellFont が定める配布形はこれだけである。実行時に読み込むバイナリ容器は定義しない。

### 11.1 描画器が提供するもの

生成されたヘッダがどの描画器でも通るように、名前を固定する。
**描画器は `<CellFont.h>` を提供し、その中で次を定義する。**

| 名前 | 内容 |
| --- | --- |
| `CellFont` / `CellGlyph` | §3 の構造体 |
| `CELLFONT_PROGMEM` | PROGMEM 属性。不要な環境では空に展開する |
| `CELLFONT_SPEC_VERSION` | 実装が従う仕様の版。本書は **1** |

### 11.2 生成ヘッダの形

```c
#include <CellFont.h>

#if !defined(CELLFONT_SPEC_VERSION) || CELLFONT_SPEC_VERSION != 1
#error "This font header requires CellFont spec version 1"
#endif

static const uint8_t   NameBitmaps[] CELLFONT_PROGMEM = { /* ... */ };
static const CellGlyph NameGlyphs[]  CELLFONT_PROGMEM = { /* ... */ };  /* 可変ピッチのみ */
static const uint16_t  NameCodes[]   CELLFONT_PROGMEM = { /* ... */ };  /* 疎のみ */
static const CellFont  Name          CELLFONT_PROGMEM = { /* ... */ };
```

- **版の確認はコンパイル時に行う。** 構造体に版を持たせない。
  焼き込み形式なので `#error` で足り、実行時のフィールド 4 バイトを払う理由がない
- **PROGMEM 属性を 4 つすべてに付ける。** ハーバードアーキテクチャ（AVR など）では
  どれか 1 つでも抜けると化ける
- 選んだ形式（固定/可変・連続/疎・連鎖の有無）とデータ量をコメントに書く

### 11.3 シンボルの命名と出力順

| 対象 | 名前 |
| --- | --- |
| 入口のフォント | `Name` |
| 連鎖の 2 本目以降 | `Name_2`, `Name_3`, … （連鎖順） |
| 各配列 | `<フォント名>Bitmaps` / `Glyphs` / `Codes`（例: `Name_2Bitmaps`） |

**名前は連鎖順、定義の出力は逆順。** C は前方参照できないので、
`next` で指される側（`Name_3` → `Name_2` → `Name`）から先に定義する。
利用者が触るのは常に `Name` の 1 つだけ。

## 12. どのサイズで使うか

**CellFont は §13 の制限内ならどのサイズでも正しく動く。** サイズは可否ではなく
効率の問題で、ここではその効率を 2 つの軸で測る。

- **データ密度**（§12.1〜12.3）— 墨面の高さ H ≈ 16 で 3 つの独立した機構が同時に反転し、
  それより上では per-glyph bbox と圧縮を持つ形式のほうがデータが小さい
- **フラッシュ総量**（§12.4）— 別形式に移すにはデコーダをもう 1 つ積む必要がある。
  **収録字数が少なければ、そのコストをデータの差が超えない**

まずデータ密度から。

### 12.1 per-glyph bbox

ASCII 95 字（連続）:

| フォント | H | CellFont | +bbox | GFXfont | u8g2 |
| --- | --- | --- | --- | --- | --- |
| DejaVu 9px | 10 | 1,141 | 1,046 | 1,030 | **945** |
| FreeSans 9pt | 18 | 2,320 | 1,843 | 1,827 | **1,692** |
| FreeSans 12pt | 23 | 3,800 | 2,662 | 2,646 | **2,209** |
| FreeSans 18pt | 35 | 7,730 | 4,852 | 4,836 | **3,336** |
| DejaVu 72px | 75 | 37,769 | 19,632 | 19,616 | **6,646** |

GFXfont の列は **C 構造体としてフラッシュに載る量**（`12 + bitmap + 7·span`）。

**bbox を足すと GFXfont になる。** 連続なら `span = n`、`codes` は空なので、
差はヘッダの 28 と 12 の差だけ。フォントの中身によらず常に **+16 バイト**
（上の 5 行すべてで厳密に +16）。
つまり**対象範囲を広げる = GFXfont を作り直す**ことになるので、広げる動機がない。

日本語混在 190 字では逆で、H ≤ 12 では bbox を足すと**増える**（2,163 → 2,514）。
16px で −9%、24px で −20%、40px で −27%。

### 12.2 圧縮

**圧縮しない。** RLE との差は **16px で 1.5%** しかなく、デコーダのバイト数に見合わない。

ただし **24px で 8%、40px で 29%、75px で 66%。**
「圧縮しない」という判断は 16px 以下の中でだけ安全で、外に出ると崩れる。

### 12.3 総量

日本語混在 190 字:

| セル | CellFont | u8g2 | bff | CellFont+bbox |
| --- | --- | --- | --- | --- |
| 4x8 / 8x9 | **1,473** | 2,201 | 2,511 | 2,514 |
| 6x12 / 12x11 | **2,708** | 3,165 | 3,301 | 3,259 |
| 8x16 / 16x16 | 4,798 | **4,408** | 4,570 | 4,474 |
| 12x24 / 24x22 | 9,257 | **7,356** | 8,158 | 8,004 |
| 20x40 / 40x38 | 24,700 | **13,429** | 19,200 | 18,958 |

**8〜12px は CellFont、16px で逆転、24px で −26%。**

### 12.4 デコーダを増やすコスト

ここまではすべて**データ量のみ**の比較である。実際には、大きなフォント 1 本のために
別形式へ移すと**デコーダをもう 1 つ積むことになる。**

その追加コストを D バイトとすると、**データの差が D を超えるまでは CellFont のほうが
総量で安い。** 差は字数に比例して増えるので、境目は字数で表せる。

| フォント | H | D=300 | D=500 | D=800 | D=1500 | 参考: 16 字での差 |
| --- | --- | --- | --- | --- | --- | --- |
| DejaVu 9px | 10 | 96+ | 96+ | 96+ | 96+ | −6 B |
| FreeSans 9pt | 18 | 48 | 77 | 96+ | 96+ | +27 B |
| FreeSans 12pt | 23 | 32 | 47 | 53 | 96+ | +79 B |
| FreeSans 18pt | 35 | 14 | 21 | 31 | 48 | +350 B |
| FreeSerif 24pt | 44 | 7 | 14 | 19 | 31 | +631 B |
| DejaVu 56px | 58 | 2 | 5 | 8 | 17 | +1,379 B |
| DejaVu 72px | 75 | 0 | 2 | 4 | 8 | +2,597 B |

数字は「CellFont のほうが総量で安い上限字数」（ASCII から数字・記号・英字の順に足して測定。
96+ は測定した全 96 字で超えなかったことを表す）。

**大きなフォントでも、字数が少なければ CellFont で持つほうが安い。**
たとえば時計表示の `0-9` と `:` の 11 字なら、24pt でも 56px でも
（D ≥ 500 の想定なら 24pt で、D ≥ 1500 なら 56px で）CellFont が勝つ。

字数が少ないほど有利になる理由は 2 つある。固定ピッチが立てばグリフ表が丸ごと消えること、
そして**共通の箱が収録字だけで決まる**ことである。数字しか入っていなければ `height` は
数字の墨面ぶんで済み、大文字や下降部のための詰め物が発生しない
（FreeSans 18pt は ASCII 全部だと H=35 だが、数字と `:` だけなら H=25）。

### 12.5 結論

| 状況 | 選ぶもの |
| --- | --- |
| H ≤ 16 | **CellFont。** データも総量も最良 |
| H > 16 かつ 字数が少ない（上表の範囲） | **CellFont。** データでは負けるがデコーダ 1 つぶんで取り返す |
| H > 16 かつ 字数が多い | per-glyph bbox と圧縮を持つ形式のほうが小さい |

D の値は描画器の実装によるので、境目を厳密に決めたい場合は
**実際に 2 つのデコーダを積んだときの増分を測ること。**

## 13. 制限

| 項目 | 上限 | 効いてくるところ |
| --- | --- | --- |
| `codes` が `uint16_t` | **U+FFFF まで**（BMP のみ） | 追加面（絵文字 U+1F300〜）は入らない |
| 可変ピッチのオフセットが 16bit | **ビットマップ 64 KB** | 大きな全文字集合で溢れる（下記） |
| `width` / `height` / `xAdvance` / `yAdvance` | 255 画素 | 実用上あたらない |
| `xOffset` / `yOffset` | −128〜127 | 実用上あたらない |
| `bytesPerGlyph` | 255 バイト | 固定ピッチは約 45×45 まで |
| `headCount` | 255 | 超える連続並びは 255 で打ち切る（正しく動く） |
| `count` | 65,535 | 実用上あたらない |

**16bit オフセットが溢れるのは可変ピッチだけ。** 固定ピッチは先頭が
`n * bytesPerGlyph` の算術なので上限がない。実測（ビットマップのみ、刈り込み方針）:

| フォント | 字数 | ビットマップ |
| --- | --- | --- |
| DejaVu 72px（ASCII 95） | 95 | 37,361 B — 収まる |
| 日本語 12px（全文字） | 4,425 | 76,628 B — **溢れる** |
| 日本語 16px（全文字） | 4,425 | 125,884 B — **溢れる** |
| 日本語 16px（大きな集合） | 10,839 | 328,240 B — **溢れる** |

## 14. 適合性

**描画器は次を満たすこと。**

- `codes` / `glyphs` / `next` の 3 つの `NULL` 判定すべてを扱う
- **固定ピッチのオフセット計算を 32bit で行う。**
  `uint16_t count * uint8_t bytesPerGlyph` を 16bit で計算すると大きな集合で壊れる
- 未収録コードでは `next` を辿り、連鎖の終端まで見てから未収録と判断する
- **未収録の描画は §6 に従う**（U+FFFD があれば描く、無ければ何も描かず送り 0）。
  独自の既定を持たない
- 連鎖の `yAdvance` は先頭のフォントのものを使う
- `width = 0` のグリフを、ビットマップを読まずに送り幅ぶんだけ進めて処理する
- `<CellFont.h>` として §11.1 の 4 つの名前を提供する

**生成器は次を満たすこと。**

- §9 のエンコーダ規範に従う
- **可変ピッチでビットマップが 65,535 バイトを超えたらエラーで落とす。**
  黙って上位を捨ててはならない
- 収録コードが U+FFFF を超えたらエラーで落とす
- `codes` が狭義単調増加であること（重複が無いこと）を検証する
- 未使用フィールドに 0 を入れる（§3）
- 連鎖を出すとき、収録集合が重ならないこと、`yAdvance` が一致することを保証する
- §11.2 の版ガードと §11.3 の命名規則に従ったヘッダを出す

## 15. 採らなかったもの

| 案 | なぜ採らなかったか |
| --- | --- |
| **グリフごとの bbox** | §12.1。H ≤ 12 では**増える**。16px 以上では効くが、そこは対象外 |
| **圧縮** | §12.2。16px で 1.5% しか縮まない。デコーダのバイト数に見合わない |
| **幅クラス表**（1〜2bit/字 + クラス記述子） | 刈り込めなくなる損が表の得を食い、16px 以上で負ける。**§9.2 の連鎖のほうが安くて強い**（形式の変更が要らない） |
| **コードの再マップ**（連番へ振り直す） | 疎索引比で 9% しか縮まないうえ、**文字列リテラルがそのまま使えなくなる** |
| **範囲表**（`{start, end, base}` の配列） | 6 バイト/範囲。実際の文字集合は散らばった 1 字が主なので、2 バイト/字のコード表より高くつく |
| **32bit オフセット** | 16bit で 64KB。超えるものは対象機に載らない。§14 のガードで足りる |
| **`codes` の 32bit 化**（追加面の対応） | 全フォントのコード表が 2 倍になる。必要なら別の形として足す |
| **構造体の version フィールド** | 焼き込み形式なので §11.2 の `#error` で同じ安全性が **0 バイト**で得られる。フィールドにすると 28 → 32 バイト |
| **オフセットの分割 2 バイト**（`offsetLo` / `offsetHi`） | `uint16_t` と同じ 4 バイトなのに、描画のたびにシフトと OR が要る。AVR でも `pgm_read_word` 1 回が 2 回になる。バイト順非依存の利点はバイナリ容器のためだが、容器は対象外 |
| **フォールバック用メトリクス**（豆腐の箱の寸法） | §6 の U+FFFD 規約で **0 バイト**。しかも豆腐を出すかどうかが文字集合の選択として表に出る |
| **`next` を描画器の API で持つ** | 4 バイト浮くが、生成ヘッダが描画器ごとの繋ぎ方を要求することになり可搬でなくなる（§7） |
| **バイナリ容器**（実行時読み込み） | 用途が対象機と食い違う。ファイルシステムを持つ機械は、字数が多ければ他形式のほうが小さい領域（§12）。magic `CEL1` のみ予約 |
