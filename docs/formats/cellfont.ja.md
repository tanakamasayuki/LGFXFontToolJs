# CellFont — ビットマップフォント形式 仕様

[English](./cellfont.en.md)

- 対象読者: この形式の生成器・描画器を実装する人
- 状態: **v1（確定）**
- 仕様版: `CELLFONT_SPEC_VERSION == 1`
- 最終更新: 2026-08-28

## 0. 位置づけ

CellFont は、フラッシュが 16〜64 KB 級のマイコンにビットマップフォントを載せるための形式。
デコーダが小さく、収録文字の増減が安く済むことを狙う。

本書は**生成器と描画器の間の取り決めだけ**を定める。両者は別の実装者でよく、
本書だけを読めば双方を実装できる。特定のライブラリやツールには依存しない。

主な対象は **1bpp・墨面の高さ 16px 以下のピクセルグリッドフォント**で、
そこでデータがいちばん密になる。**より大きなサイズでも使えるし、収録字数が少なければ
総量で有利なことも多い**（§13）。

**CellFont はコンパイル時形式である。** データは C ソースとしてファームウェアに焼き込まれ、
実行時に読み込む容器は定義しない（§12）。将来容器を定義する場合に備えて
magic `CEL1` だけを予約する。

名前は「全グリフが 1 つの**セル**を共有し、字ごとに持つのは変わるものだけ」から。
エンコーダ規範（§10）もこの語で説明できる。

## 1. 設計目標

1. **選択は実行時ではなく生成時に済ませ、結果をデータで表す。**
   描画器は生成時に選ばれた分岐を辿るだけでよく、**形式選択のための全グリフ走査を行わない**
   （疎索引では二分探索を、未収録時には連鎖の走査を行う）。
2. **収録文字の増減が安い。** 1 字足したときの増分が、その 1 字の実費に比例すること。
   範囲が飛んだだけで桁が変わる形式は使えない（§11）。
3. **描画器が小さい。** 表現力よりデコーダのバイト数を優先する。
   圧縮を持たないのはこのため（§13.2）。

## 2. 中心の考え方

決めることは 3 つ。どれも **ポインタが `NULL` かどうか**で表す。

| 選択 | `NULL` のとき | 非 `NULL` のとき |
| --- | --- | --- |
| `codes`（索引） | **連続** — `first` から `count` 個 | **疎** — コード表を二分探索 |
| `glyphs`（グリフ表） | **固定ピッチ** — 全グリフ共通の幅・送り幅 | **可変ピッチ** — 4 バイト/字 |
| `next`（連鎖） | **終端** | この表に無ければ次のフォントを見る |

**グリフごとに持つのは「変わるもの」だけ。**
高さ・`xOffset`・`yOffset` は全グリフ共通で、これが per-glyph bbox を持つ形式との一番の差。
共通なので ascent が定数になり、フォント設定時に全グリフを走査する必要がない。

組み合わせすべてを 1 つのデコーダが扱う。分岐は各 1 か所。

## 3. 構造

```c
typedef struct CellGlyph {   /* 可変ピッチのときだけ。4 バイト固定 */
  uint16_t offset;             /* bitmap 先頭からのバイトオフセット */
  uint8_t  width;              /* グリフの幅（画素）。0 も合法（§5） */
  uint8_t  xAdvance;           /* 送り幅（画素） */
} CellGlyph;

typedef struct CellFont {
  const uint8_t*         bitmap;      /* グリフのビット列 */
  const CellGlyph*       glyphs;      /* NULL = 固定ピッチ */
  const uint16_t*        codes;       /* NULL = 連続索引。長さ count - headCount */
  const struct CellFont* next;        /* NULL = 連鎖の終端 */
  uint16_t first;                     /* 連続索引の先頭 / 疎索引では頭ブロックの先頭 */
  uint16_t count;                     /* 収録グリフ数 */
  uint8_t  width, height;             /* width は固定ピッチ用。height は全グリフ共通 */
  uint8_t  xAdvance, yAdvance;        /* xAdvance は固定ピッチ用。yAdvance は行送り */
  int8_t   xOffset, yOffset;          /* 全グリフ共通 */
  uint8_t  bytesPerGlyph;             /* 固定ピッチ用。実行時に除算しないため */
  uint8_t  headCount;                 /* 疎索引の頭ブロック長（1 以上）。連続索引では 0 */
} CellFont;
```

ヘッダの大きさは **ABI 依存**である。C 言語が保証する値ではない。

| ABI | `sizeof(CellFont)` |
| --- | --- |
| 一般的な ILP32（32bit ポインタ、ポインタのアライメント 4） | **28 バイト** |
| 一般的な 16bit ポインタ ABI | **20 バイト** |

実際の値は対象 ABI の `sizeof(CellFont)` に従う。本書のデータ量の式と比較表は、
断りのない限り **ILP32 を前提**とした参考値である。

`bytesPerGlyph` は固定ピッチのとき `ceil(width * height / 8)` に等しい。
実行時に掛け算・割り算をしないために持つ。

**`headCount` のコストは ABI による。**

| ABI | `headCount` 無し | 有り | 差 |
| --- | --- | --- | --- |
| ILP32（自然アライメント） | 28 | 28 | **0** — 末尾の詰め物に収まる |
| 16bit ポインタ（全型アライメント 1） | 19 | 20 | **+1** — 吸収する詰め物が無い |

ILP32 では実質無料だが、AVR のようにアライメントが 1 の ABI では素直に 1 バイト増える。
`CellGlyph` は両 ABI とも 4 バイト（ILP32 ではアライメント 2）。

これらは C 言語一般の保証ではないので、描画器は対象 ABI で
`static_assert(sizeof(CellGlyph) == 4, ...)` 等により確認すること。

**未使用のフィールドには必ず 0 を入れる。** 決定性（§10.4）のために必要。

| 状況 | 0 にするフィールド |
| --- | --- |
| 固定ピッチ（`glyphs == NULL`） | なし |
| 可変ピッチ | `width`, `xAdvance`, `bytesPerGlyph` |
| 連続索引（`codes == NULL`） | `headCount` |

疎索引では `first` と `headCount` をともに必ず使う（`headCount >= 1`、§10.3）。

## 4. 描画座標系

**ペン位置 `(penX, penY)` は行のベースライン上の点とする。座標は右および下を正とする。**

1. グリフのビットマップ左上画素を `(penX + xOffset, penY + yOffset)` に置く
2. ビットマップは `width` 列 × `height` 行を占める
3. 描画後、`penX` を送り幅だけ進める（固定ピッチは `CellFont.xAdvance`、
   可変ピッチは `glyphs[n].xAdvance`）
4. 次の行の `penY` は、**連鎖先頭フォントの** `yAdvance` だけ進める

`xOffset` / `yOffset` は負でよい。負のとき箱はペン位置より左・上へ張り出す。
**典型的には `yOffset` は負**で、箱はベースラインの上にある。

派生する定数（フォントごとに一定）:

```text
ascent  = -yOffset            ベースラインから箱の上端まで
descent = height + yOffset    ベースラインから箱の下端まで
```

行の上端を基準とする描画 API では `penY = lineTop + ascent` とする。

連鎖する各フォントは `height` / `xOffset` / `yOffset` を別々に持ってよい（§8）。
**ベースラインは連鎖全体で共通**なので、各フォントの `yOffset` をそのまま使えば字面は揃う。

## 5. ビットマップの並び

**1bpp 専用。ビットが 1 の画素が墨。** 行は上から下へ、各行は左から右へ MSB first。
行を連結したビット列で、**行の途中ではバイト境界に揃えない。
グリフの先頭だけがバイト境界に揃う。**

1 グリフのバイト数は `ceil(width * height / 8)`。

- **固定ピッチ**: グリフ `n` の先頭は `bitmap + n * bytesPerGlyph`。表を引かない
- **可変ピッチ**: グリフ `n` の先頭は `bitmap + glyphs[n].offset`

グリフの高さは常に `height`、描画位置は常に `xOffset` / `yOffset`。
つまり**すべてのグリフが同じ高さの箱に入っている。**

**幅が 0 のグリフは合法。** 空白は実際のフォントでは墨面を持たない
（調べた範囲のすべてのフォントで `0x0` + 非ゼロの送り幅）。

- 可変ピッチでは `width = 0` とし、ビットマップを 1 バイトも消費しない。
  その `offset` は次のグリフの `offset` と同値でよい
- 固定ピッチでは全グリフが `width` 幅なので、空白は**空のセル**（すべて 0 のビット列）になる。
  §10.1 のセル規則が自動的にそうする

**`width` が `xAdvance` を超えてよい**（張り出し）。描画は `width` 列ぶん、
ペンの前進は `xAdvance` ぶん。

グリフの最終バイトに余る下位ビットは **0 でなければならない**（正準出力のため。§10.4）。

画素のビット順は GFXfont と同じである。**ただしビットマップをそのまま流用できるとは限らない。**
GFXfont はグリフごとに `width` / `height` / `xOffset` / `yOffset` を持つのに対し、
CellFont は高さとオフセットが共通なので、共通セルへ正規化する際に
**各グリフの再配置とパディングを伴うビットマップの再構築が要る。**

実フォントで確かめると、FreeSans 12pt は 18 種類のグリフ高さと 11 種類の `yOffset` を持つ。
**同じ寸法とオフセットを既に全グリフが持つ資産に限り**、ビット列をそのまま流用できる。

## 6. グリフの並び順

ビットマップ・グリフ表は次の順に並ぶ。**コード表もこの順に対応する。**

1. **頭ブロック** — `first` から `headCount` 個の連続したコード（`codes` には現れない）
2. **しっぽ** — 残りのコードを**昇順**に。`codes[0 .. count-headCount-1]` が対応する

連続索引（`codes == NULL`）のときは頭ブロックだけで、`headCount` は使わない。

**`codes` は狭義単調増加でなければならない**（重複禁止）。二分探索の前提であり、
破ると静かに別のグリフが出る。頭ブロックのコードは `codes` に現れない。

## 7. 索引

### 7.1 1 つのフォントを引く

構造体は PROGMEM 上に置かれうるので、**全フィールドを `CELLFONT_READ_*` 経由で読む**
（§12.1）。フラットメモリでは素の間接参照に展開されるので、コストは増えない。

グリフ番号は最大 65,534 になりうる。`int` が 16bit の環境では負値と両立しないので、
**見つかったかどうかは戻り値、番号は出力引数**で返す。

```c
/* 見つかれば 1 を返し *outIndex に格納。見つからなければ 0。 */
int cellFontIndex(const CellFont* f, uint16_t c, uint16_t* outIndex) {
  const uint16_t  first = CELLFONT_READ_U16(&f->first);
  const uint16_t  count = CELLFONT_READ_U16(&f->count);
  const uint16_t* codes = (const uint16_t*)CELLFONT_READ_PTR(&f->codes);

  if (codes == NULL) {                             /* 連続 */
    if (c < first) return 0;
    uint16_t rel = (uint16_t)(c - first);          /* 加算しないので 16bit でも安全 */
    if (rel >= count) return 0;
    *outIndex = rel;
    return 1;
  }

  uint8_t head = CELLFONT_READ_U8(&f->headCount);
  if (head != 0 && c >= first) {                   /* 疎・頭ブロック */
    uint16_t rel = (uint16_t)(c - first);
    if (rel < head) { *outIndex = rel; return 1; }
  }

  uint16_t lo = 0, hi = (uint16_t)(count - head);  /* 疎・しっぽ */
  while (lo < hi) {
    uint16_t mid = (uint16_t)(lo + ((hi - lo) >> 1));   /* lo+hi はラップしうる */
    uint16_t v = CELLFONT_READ_U16(&codes[mid]);
    if (v == c) { *outIndex = (uint16_t)(head + mid); return 1; }
    if (v < c) lo = (uint16_t)(mid + 1); else hi = mid;
  }
  return 0;
}
```

**16bit 環境での注意。** `first + count` や `lo + hi` をそのまま書くと `int` が 16bit の
環境でラップする。特に二分探索の中央は `count > 32768` の疎フォントで実際に踏む
（`lo=0x8000, hi=0xFFFF` のとき `(lo+hi)>>1` は `0x3FFF`、正しくは `0xBFFF`）。
**上のように減算形で書くこと。**

**しっぽのコードは `first` より小さいことがある。** 頭ブロックは最長の連続並びであって
最小のコードとは限らない（§10.3）。`c < first` で早期に打ち切ってよいのは連続索引のときだけ。

### 7.2 連鎖を引く

```text
find(chain, c):
  各フォント f を next 順に辿り、cellFontIndex(f, c) が成功したらそれを返す

描画:
  1. find(chain, c) が見つかればそれを描く
  2. 見つからず、かつ c != U+FFFD なら find(chain, U+FFFD) を試す
  3. それも見つからなければ何も描かず、ペンを進めない（送り幅 0）
```

**U+FFFD への退避は連鎖全体を引き終えてから行う。** フォントごとに退避してはならない
（1 本目に無く 2 本目にある字が、1 本目の U+FFFD で潰れてしまう）。
要求コード自体が U+FFFD のときは再検索しない。

形式にフォールバック用のメトリクスを持たせない。豆腐を出すかどうかは
「文字集合に U+FFFD を入れるか」という**生成時の選択**になり、結果はデータに現れる（§1 目標 1）。
描画器が独自の既定を持つと同じフォントが実装ごとに違って見えるので、ここは規範とする。

**頭ブロックを持つ理由。** 現実の文字集合は「ASCII 全部 + 記号数個」という形になる。
全体を疎にすると、連続している ASCII 95 字にも 2 バイト/字のコード表が付く。
頭を切り出すとそこが丸ごと消える。

| | 全体を疎 | 頭 + しっぽ | 削減 |
| --- | --- | --- | --- |
| 4x8 ASCII 95 字 + 記号 6 字 | 990 B | **800 B** | −19.2% |
| 6x12 ASCII 95 字 + 記号 6 字 | 1,442 B | **1,252 B** | −13.2% |

## 8. 連鎖（`next`）

`next` を辿る順に探し、**最初に見つかったフォントが勝つ。**
生成器は収録集合が重ならないように出す。

連鎖する各フォントは `height` / `xOffset` / `yOffset` を別々に持ってよい
（幅の違うグリフ群は墨面の高さも違う）。
ただし **`yAdvance` は連鎖全体で一致していなければならない。**
行送りが揃わないと段組みが壊れる。先頭のフォントの `yAdvance` を正とする。

連鎖が要る理由は §10.2 と §11。**`next` を描画器の API（フォントの配列）ではなく
構造体に置くのは、連鎖が §1 の目標 2 を成立させている仕組みだからである。**
API に置くと、生成したヘッダが描画器ごとに違う繋ぎ方を要求することになり、
可搬でなくなる。代償はフォント 1 本あたり 4 バイト（16bit ポインタなら 2 バイト）で、
連鎖が生む削減（8px の日本語 190 字で 690 B）に対して 1% 程度。

## 9. データ量

記号を次のように置く。**可変ピッチではグリフごとに幅が違うので、1 字あたりの b は
一定にならない。**総量 B で表す。

```text
n = グリフ数
h = 頭ブロック長
H = sizeof(CellFont)                          ILP32 なら 28
b = ceil(width * height / 8)                  固定ピッチの 1 字分
B = Σ ceil(width_i * height / 8)              ビットマップの総バイト数
```

| 形式 | データ量 |
| --- | --- |
| 固定ピッチ・連続 | H + n·b |
| 固定ピッチ・頭 + 疎 | H + n·b + 2(n−h) |
| 固定ピッチ・疎 | H + n·(b+2) |
| 可変ピッチ・連続 | H + B + 4n |
| 可変ピッチ・頭 + 疎 | H + B + 4n + 2(n−h) |
| 可変ピッチ・疎 | H + B + 6n |

固定ピッチでは全グリフの幅が等しいので `B = n·b` となり、上 3 行は下 3 行の特別な場合になる。

参考として GFXfont は `12 + B_gfx + 7·span`。**GFXfont もグリフごとに幅と高さが違う**ので、
1 字あたりの `b` ではなく総量で表す。`B_gfx` は GFXfont の各グリフのビットマップ長の合計で、
**CellFont の `B` とは一致しない**（GFXfont は墨面の箱、CellFont は共通の高さのセル）。
`span` は `first`〜`last` の**範囲**であってグリフ数ではない。U+4E00〜U+9FA5 に散った 500 字を収めるには 20,902 件のグリフ表
（**146 KB**）が要る。**疎索引が桁違いに効くのはここ。**

## 10. エンコーダ規範

同じ入力から常に同じデータが出るために、生成器は次に従う。

### 10.1 セル候補と刈り込み候補

CellFont には**グリフごとの `xOffset` が無い**ので、各グリフの左端を独立に刈ることはできない。
「刈り込み」の意味を先に定める。

**境界の計算には墨のあるグリフだけを使う**（幅・高さがともに 1 以上のもの）。
無墨グリフ（空白など）の `xOffset` / `yOffset` は書体によって任意の値を取るので、
含めると共通の箱が無駄に広がる。

```text
墨のあるグリフについて
  L   = min(xOffset_i)                     共通の左端
  T   = min(yOffset_i)                     共通の上端
  B   = max(yOffset_i + 墨面の高さ_i)      共通の下端
  R_i = xOffset_i + 墨面の幅_i             グリフ i の墨面右端

出力する共通メトリクス
  xOffset = L,  yOffset = T,  height = B - T

グリフ幅
  セル候補     : width_i = max(xAdvance_i, R_i - L)
  刈り込み候補 : width_i = R_i - L

画素の再配置
  入力グリフ i の画素 (x, y) を、出力セルの (x + xOffset_i - L, y + yOffset_i - T) へ置く。
  それ以外の画素は 0。

無墨グリフ
  セル候補     : width_i = xAdvance_i（全画素 0）
  刈り込み候補 : width_i = 0

墨のあるグリフが 1 つも無い場合（上の無墨グリフ規則にかかわらず、こちらを優先する）
  xOffset = 0, yOffset = 0, height = 1, 全 width = 0, bitmap = NULL
```

### 候補の作り方

**候補は「まとめ方」で、方針はグループごとに選ぶ。** 連鎖の各フォントは独立なので、
セルか刈り込みかはフォント全体で 1 つに決めるものではない。

```text
まとめ方（候補）
  1. 単一            全グリフを 1 本に
  2. セル幅クラス     (セル幅, xAdvance) が同じものごとに分ける
  3. 刈り込み幅クラス (墨面幅, xAdvance) が同じものごとに分ける

各グループごとに、セル候補と刈り込み候補の小さいほうを採る。
候補全体の大きさ = Σ（sizeof(CellFont) + 各配列）
```

**表現可能な候補をすべて構築し、合計が最小のものを採る。** 同値のときは §10.4。

グループごとに選べることは効く。4x8 の日本語 190 字では、先にセル／刈り込みを決めてから
連鎖を検討すると 1,620 B、まとめ方だけを候補にしてグループごとに選ぶと **1,473 B**。

**これ以外の分割は探索しない。** 幅クラス以外の任意の集合分割や、3 段以上の最適化は
v1 の対象外とする。

### 連鎖の本数は生成器の方針

**形式は連鎖の長さを制限しない。** 描画器は `next` が `NULL` になるまで辿るだけで、
2 本でも 23 本でも実装は同じ。§15.1 の不変条件にも本数は出てこない。

一方で本数は**実行時コストに直結する**。後段のフォントに載る字は、前段すべてを
引き外してから見つかる。未収録の字は毎回全本数を走査し、U+FFFD 退避（§7.2）で
もう一周する。

したがって**上限は生成器のオプション**とし、`maxChain` と呼ぶ。**既定は 2**。

実測（日本語 190 字、上限 2 と無制限）:

| セル | 上限 2 | 無制限 | 1 文字あたりの探索回数 |
| --- | --- | --- | --- |
| 4x8 / 8x9 | **1,473**（2 本） | 1,473（2 本） | 1.5 → 1.5 |
| 8x16 / 16x16 | **4,798**（2 本） | 4,501（15 本） | 1.5 → 6.1 |
| 12x24 / 24x22 | **9,257**（2 本） | 8,416（18 本） | 1.5 → 7.1 |
| 20x40 / 40x38 | **24,700**（2 本） | 22,320（23 本） | 1.5 → 8.3 |

**データ量で 6〜10% 得をする代わりに、探索回数が 4〜6 倍になる。**
対象機に実際に載る 8〜12px では上限 2 でも利得を取りこぼさないので、既定を 2 とする。
データ量を最優先する利用者は上限を上げられる。

| 4x8 の ASCII 95 字 | 刈り込み候補 | セル候補 |
| --- | --- | --- |
| データ量 | 可変ピッチ 726 B | **固定ピッチ 408 B** |

セル候補が勝つのは、刈り込むと `i` と `W` で幅が変わって固定ピッチ判定が落ち、
4 バイト/字のグリフ表が付くため。**表が丸ごと消えるほうが詰め物より大きい。**
**ただし大きいフォントでは逆転する**（詰め物が表より高くつく）ので、必ず両方を測る。

### 10.2 セル幅クラスで分け、`next` でつなぐ

幅の違うグリフが混ざったフォントは、**1 本にまとめると固定ピッチ判定がまず通らない。**
`(width, xAdvance)` が同じものごとに分けて連鎖すると、各フォントが固定ピッチになり
グリフ表が消える。

| 190 字（ASCII 95 + 全角 95） | 連鎖 | 単一 | クラス数 |
| --- | --- | --- | --- |
| 4x8 / 8x9 | **1,473 B** | 2,163 B | 2 |
| 6x12 / 12x11 | **2,708 B** | 3,245 B | 2 |
| 8x16 / 16x16 | **4,798 B** | 4,924 B | 2 |
| 12x24 / 24x22 | **9,257 B** | 9,972 B | 2 |
| 20x40 / 40x38 | **24,700 B** | 25,958 B | 2 |

**小さいフォントほど効く。** クラス数が多い書体（比例欧文など）では分けても得にならないので、
生成器は**両方を計算して小さいほうを採る。**

クラスごとに分けたとき、各フォントは固定ピッチになる:

| | CellFont | 参考: u8g2 |
| --- | --- | --- |
| 4x8 固定・連続 95 字 | **408 B** | 764 B |
| 8x9 固定・頭+疎 95 字 | **1,065 B** | 1,390 B |
| 8x16 固定・連続 95 字 | 1,548 B | **1,282 B** |
| 16x16 固定・頭+疎 95 字 | 3,250 B | **3,100 B** |

### 10.3 索引とグリフ表の選択

利用者に選ばせない。**入力を見て小さいほうを選ぶ。**

| 判定 | 結果 |
| --- | --- |
| 全グリフの `width` と `xAdvance` が同一で、かつ `ceil(width * height / 8) <= 255` | `glyphs = NULL`、`bytesPerGlyph` を設定 |
| 上の幅・送り幅は同一だが `ceil(width * height / 8) > 255` | **可変ピッチにする**（エラーにしない） |
| 収録コードが連続 | `codes = NULL`、`headCount = 0` |
| 疎 | **最長の連続並び**を頭ブロックにする（`first` = その先頭）。長さ 1 でもよい |

**`bytesPerGlyph` は 8bit なので、固定ピッチは 1 グリフ 255 バイトまで**（`width * height <= 2040`、
おおむね 45×45）。46×46 や 32×64 はこれを超えるので、幅が揃っていても固定ピッチにできない。
可変ピッチなら `bytesPerGlyph` を使わないので表現できる。

**長さ 1 の頭ブロックにも意味がある。** `first` と `headCount` は元からあるフィールドなので
追加コストは 0 で、`codes` が 1 件（2 バイト）減る。デコーダも変わらない。
したがって疎索引では常に `headCount >= 1` になる（`count >= 1` なので必ず取れる）。

逆に `headCount == count` になることはない。全コードが `first` から連続なら、
それは疎ではなく連続索引だからである。よって**疎索引のしっぽは必ず 1 件以上**あり、
`codes` が長さ 0 になることはない。

頭ブロックが 255 を超えるときは 255 で打ち切る。残りはしっぽに入り、正しく動く。

**頭ブロックは最長の連続並びであって、最小のコードとは限らない。**
最長の並びが中間にあれば `first` はそこを指し、しっぽには `first` より小さいコードが混ざる。

### 10.4 正準出力

**同じ入力からはバイト一致の出力が出ること。**

ここでいう「同じ入力」とは次の 3 つである。共通セルへの正規化（§10.1）は
生成器の仕事であって、入力の一部ではない。

| 入力 | 内容 |
| --- | --- |
| **正規化前のグリフ集合** | 各グリフはコードポイント・画素・墨面の幅と高さ・`xAdvance`・`xOffset`・`yOffset` を持つ |
| **フォント共通の `yAdvance`** | グリフからは導けないので入力に含める |
| **対象 ABI の `sizeof(CellFont)`** | 候補比較に使う（下記）。既定は ILP32 の 28 |
| **`maxChain`** | 連鎖の本数の上限（§10.2）。既定 2。値が変われば選ばれる候補が変わる |

**対象 ABI を入力に含めるのは、これが候補の勝敗を実際に変えるためである。**
連鎖候補はフォント 1 本ごとにヘッダが増えるので、`H` が変わると順位が入れ替わる。
実測では 4x12 / 12x11 の日本語 190 字で、`H = 28` ならセル候補・連鎖（2,708 B）、
`H = 20` なら刈り込み候補・連鎖（2,626 B）が勝った。

したがって**「同じ入力からバイト一致」は同じ対象 ABI の中でのみ成立する。**
クロスコンパイルする生成器は、実行中のホストの `sizeof(CellFont)` を使ってはならない。

**基本規則**

- コードポイントを昇順にソートしてから並べる（入力の順序に依存しない）
- 出力にタイムスタンプ・絶対パス・ホスト名・生成器のバージョンを含めない
- 16 進の桁数・1 行あたりのバイト数・改行・末尾改行を固定する
- 浮動小数を出力に出さない

**同値のときの選択（タイブレーク）**

規則が無いと、適合する出力が複数できてしまう。次で一意に決める。

| 場面 | 規則 |
| --- | --- |
| 同じ長さの最長連続区間が複数ある | **コードポイントが小さいほう**を頭ブロックにする |
| 可変ピッチの `offset` | **そのグリフを出力する直前のビットマップ配列長**とする（＝先行グリフのバイト数の累積） |
| `width == 0` のグリフの `offset` | 同じ規則。**次のグリフがあれば**その `offset` と同値になる（末尾なら総バイト数と同値） |
| グリフ最終バイトの余りビット | **0**（§5） |
| 幅クラスを連鎖する順序 | 各クラスの**最小コードポイントの昇順** |

**候補の順位付け**

§10.1 の 4 候補は、複数の軸が同時に違いうる。軸ごとに独立した規則を置くと、
規則どうしが逆の候補を指しうるので、**上から順に適用する辞書順**として定める。
先に差がついた時点で決まり、下位の基準は見ない。

| 順 | 基準 |
| --- | --- |
| 1 | **合計バイト数が小さい**（`sizeof(CellFont)` × フォント数 + 各配列） |
| 2 | **フォント本数が少ない** |
| 3 | **固定ピッチのフォント数が多い** |
| 4 | **セル候補である** |

基準 2 を 3 より先に置くのは、連鎖の長さが**あらゆる描画で効く**ためである。
後段のフォントに載る字は、前段すべてを引き外してからでないと見つからない。
固定ピッチが節約するのは 1 描画あたりの表参照 1 回で、影響が小さい。

基準 4 まで適用すれば必ず 1 つに決まる。基準 2 が単一／連鎖を、基準 4 がセル／刈り込みを
落とすため。連鎖が 1 本に退化した場合、その候補は単一候補と同一の出力になるので
区別する必要がない。

## 11. 収録文字の増減

**この形式のいちばん重要な性質。** 4x8 の ASCII 95 字から文字を足したときの増分:

| 文字集合 | n | CellFont | Δ | 参考: GFXfont | Δ | 参考: u8g2 | Δ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ASCII 95 字 | 95 | 408 | — | 889 | — | 764 | — |
| +1 字 | 96 | **437** | **+29** | 1,240 | +351 | 780 | +16 |
| +5 字 | 100 | **477** | **+40** | 60,180 | **+58,940** | 822 | +42 |
| +10 字 | 105 | **528** | **+51** | 87,806 | +27,626 | 864 | +42 |
| +20 字 | 115 | **648** | **+120** | 247,696 | +159,890 | 1,038 | +174 |
| +30 字 | 125 | **758** | **+110** | 271,430 | +23,734 | 1,195 | +157 |

GFXfont は範囲が飛んだ瞬間に桁が変わる（1 字足すのに 58,940 バイト）。
CellFont は疎索引と連鎖によって、増分が**その字の実費に比例する。**

この性質を成立させているのは 3 つ。

1. **疎索引**（§2）— 収録コードが飛んでいても表は 2 バイト/字
2. **頭ブロック**（§7）— 連続部分にはコード表が付かない
3. **セル幅クラスでの連鎖**（§10.2）— 幅の違う字を足しても、既存のフォントは固定ピッチのまま

3 が無いと、ASCII だけのフォントに幅の違う字を 1 つ足しただけで固定ピッチ判定が落ち、
全グリフに 4 バイトの表が付いて **+394 バイト**になる。連鎖があれば **+29 バイト**。

## 12. C ソース出力

CellFont が定める配布形はこれだけである。実行時に読み込むバイナリ容器は定義しない。

### 12.1 描画器が提供するもの

生成されたヘッダがどの描画器でも通るように、名前を固定する。
**描画器は `<CellFont.h>` を提供し、その中で次を定義する。**

| 名前 | 内容 |
| --- | --- |
| `CellFont` / `CellGlyph` | §3 の構造体 |
| `CELLFONT_PROGMEM` | PROGMEM 属性。不要な環境では空に展開する |
| `CELLFONT_READ_U8(p)` | PROGMEM 上の `uint8_t` を読む |
| `CELLFONT_READ_U16(p)` | PROGMEM 上の `uint16_t` を読む |
| `CELLFONT_READ_PTR(p)` | PROGMEM 上のポインタを読む |
| `CELLFONT_SPEC_VERSION` | 実装が従う仕様の版。本書は **1** |

**`CellFont` 構造体自身が PROGMEM 上に置かれる**（§12.2）ので、
`f->first` のような素の参照ではハーバードアーキテクチャで正しく読めない。
**構造体・グリフ表・コード表・ビットマップのすべての読み出しをアクセサ経由にする。**
`codes` / `glyphs` / `next` の `NULL` 判定も、`CELLFONT_READ_PTR` で読んだ値に対して行う。

フラットメモリの環境では 3 つとも素の間接参照に展開してよい（コストは増えない）。

### 12.2 生成ヘッダの形

```c
#pragma once
#include <CellFont.h>

#if !defined(CELLFONT_SPEC_VERSION) || CELLFONT_SPEC_VERSION != 1
#error "This font header requires CellFont spec version 1"
#endif

static const uint8_t   NameBitmaps[] CELLFONT_PROGMEM = { /* ... */ };
static const CellGlyph NameGlyphs[]  CELLFONT_PROGMEM = { /* ... */ };  /* 可変ピッチのみ */
static const uint16_t  NameCodes[]   CELLFONT_PROGMEM = { /* ... */ };  /* 疎のみ */
static const CellFont  Name          CELLFONT_PROGMEM = { /* ... */ };
```

- **版の確認はコンパイル時に行う。** 構造体に版を持たせない。
  焼き込み形式なので `#error` で足り、実行時のフィールド 4 バイトを払う理由がない
- **PROGMEM 属性を 4 つすべてに付ける。** ハーバードアーキテクチャ（AVR など）では
  どれか 1 つでも抜けると化ける
- **`#pragma once`（または include ガード）を必ず出す。**
  同じ翻訳単位から複数回 include されても再定義にならないようにする
- 選んだ形式（固定/可変・連続/疎・連鎖の有無）とデータ量をコメントに書く

**`static const` は翻訳単位ごとに実体を持つ。** 2 つの `.c` / `.cpp` から同じフォントヘッダを
include すると、**フォントデータがフラッシュに 2 個載る。** 複数の翻訳単位から使うときは、
1 つの翻訳単位だけで include して `extern` で公開するか、リンカの重複排除に頼らない形にする。
利用者に伝わるよう、生成ヘッダのコメントに一言入れるとよい。

### 12.3 シンボルの命名と出力順

| 対象 | 名前 |
| --- | --- |
| 入口のフォント | `Name` |
| 連鎖の 2 本目以降 | `Name_2`, `Name_3`, … （連鎖順） |
| 各配列 | `<フォント名>Bitmaps` / `Glyphs` / `Codes`（例: `Name_2Bitmaps`） |

**名前は連鎖順、定義の出力は逆順。** C は前方参照できないので、
`next` で指される側（`Name_3` → `Name_2` → `Name`）から先に定義する。
利用者が触るのは常に `Name` の 1 つだけ。

## 13. どのサイズで使うか

**CellFont は §14 の制限内ならどのサイズでも正しく動く。** サイズは可否ではなく
効率の問題で、ここではその効率を 2 つの軸で測る。

- **データ密度**（§13.1〜13.3）— 墨面の高さ H ≈ 16 で 3 つの独立した機構が同時に反転し、
  それより上では per-glyph bbox と圧縮を持つ形式のほうがデータが小さい
- **フラッシュ総量**（§13.4）— 別形式に移すにはデコーダをもう 1 つ積む必要がある。
  **収録字数が少なければ、そのコストをデータの差が超えない**

まずデータ密度から。

### 13.1 per-glyph bbox

ASCII 95 字（連続）:

| フォント | H | CellFont | +bbox | GFXfont | u8g2 |
| --- | --- | --- | --- | --- | --- |
| DejaVu 9px | 10 | 1,141 | 1,046 | 1,030 | **945** |
| FreeSans 9pt | 18 | 2,320 | 1,843 | 1,827 | **1,692** |
| FreeSans 12pt | 23 | 3,800 | 2,662 | 2,646 | **2,209** |
| FreeSans 18pt | 35 | 7,730 | 4,852 | 4,836 | **3,336** |
| DejaVu 72px | 75 | 37,769 | 19,632 | 19,616 | **6,646** |

GFXfont の列は **C 構造体としてフラッシュに載る量**（`12 + B_gfx + 7·span`、§9）。

**bbox を足すと GFXfont になる。** 連続なら `span = n`、`codes` は空なので、
差はヘッダの 28 と 12 の差だけ。フォントの中身によらず常に **+16 バイト**
（上の 5 行すべてで厳密に +16）。
つまり**対象範囲を広げる = GFXfont を作り直す**ことになるので、広げる動機がない。

日本語混在 190 字では逆で、H ≤ 12 では bbox を足すと**増える**（2,163 → 2,514）。
16px で −9%、24px で −20%、40px で −27%。

### 13.2 圧縮

**圧縮しない。** RLE との差は **16px で 1.5%** しかなく、デコーダのバイト数に見合わない。

ただし **24px で 8%、40px で 29%、75px で 66%。**
「圧縮しない」という判断は 16px 以下の中でだけ安全で、外に出ると崩れる。

### 13.3 総量

日本語混在 190 字:

| セル | CellFont | u8g2 | bff | CellFont+bbox |
| --- | --- | --- | --- | --- |
| 4x8 / 8x9 | **1,473** | 2,201 | 2,511 | 2,514 |
| 6x12 / 12x11 | **2,708** | 3,165 | 3,301 | 3,259 |
| 8x16 / 16x16 | 4,798 | **4,408** | 4,570 | 4,474 |
| 12x24 / 24x22 | 9,257 | **7,356** | 8,158 | 8,004 |
| 20x40 / 40x38 | 24,700 | **13,429** | 19,200 | 18,958 |

**8〜12px は CellFont、16px で逆転、24px で −26%。**

### 13.4 デコーダを増やすコスト

ここまではすべて**データ量のみ**の比較である。実際には、大きなフォント 1 本のために
別形式へ移すと**デコーダをもう 1 つ積むことになる。**

その追加コストを D バイトとすると、**データの差が D を超えるまでは CellFont のほうが
総量で安い。** 差は字数に比例して増えるので、境目は字数で表せる。

| フォント | H | D=300 | D=500 | D=800 | D=1500 | 参考: 16 字での差 |
| --- | --- | --- | --- | --- | --- | --- |
| DejaVu 9px | 10 | 96+ | 96+ | 96+ | 96+ | −6 B |
| FreeSans 9pt | 18 | 48 | 77 | 96+ | 96+ | +27 B |
| FreeSans 12pt | 23 | 32 | 47 | 53 | 96+ | +79 B |
| FreeSans 18pt | 35 | 14 | 21 | 31 | 48 | +350 B |
| FreeSerif 24pt | 44 | 7 | 14 | 19 | 31 | +631 B |
| DejaVu 56px | 58 | 2 | 5 | 8 | 17 | +1,379 B |
| DejaVu 72px | 75 | 0 | 2 | 4 | 8 | +2,597 B |

数字は「CellFont のほうが総量で安い上限字数」（ASCII から数字・記号・英字の順に足して測定。
96+ は測定した全 96 字で超えなかったことを表す）。

**大きなフォントでも、字数が少なければ CellFont で持つほうが安い。**
たとえば時計表示の `0-9` と `:` の 11 字なら、24pt でも 56px でも
（D ≥ 500 の想定なら 24pt で、D ≥ 1500 なら 56px で）CellFont が勝つ。

字数が少ないほど有利になる理由は 2 つある。固定ピッチが立てばグリフ表が丸ごと消えること、
そして**共通の箱が収録字だけで決まる**ことである。数字しか入っていなければ `height` は
数字の墨面ぶんで済み、大文字や下降部のための詰め物が発生しない
（FreeSans 18pt は ASCII 全部だと H=35 だが、数字と `:` だけなら H=25）。

### 13.5 結論

| 状況 | 選ぶもの |
| --- | --- |
| H ≤ 16 | **CellFont。** データも総量も最良 |
| H > 16 かつ 字数が少ない（上表の範囲） | **CellFont。** データでは負けるがデコーダ 1 つぶんで取り返す |
| H > 16 かつ 字数が多い | per-glyph bbox と圧縮を持つ形式のほうが小さい |

D の値は描画器の実装によるので、境目を厳密に決めたい場合は
**実際に 2 つのデコーダを積んだときの増分を測ること。**

## 14. 制限

| 項目 | 上限 | 効いてくるところ |
| --- | --- | --- |
| `codes` が `uint16_t` | **U+FFFF まで**（BMP のみ） | 追加面（絵文字 U+1F300〜）は入らない |
| 可変ピッチのオフセットが 16bit | **各グリフの開始位置が 65,535 まで** | 大きな全文字集合で溢れる（下記） |
| `width` / `height` / `xAdvance` / `yAdvance` | 255 画素 | 実用上あたらない |
| `xOffset` / `yOffset` | −128〜127 | 実用上あたらない |
| `bytesPerGlyph` | 255 バイト | 固定ピッチは約 45×45 まで |
| `headCount` | 255 | 超える連続並びは 255 で打ち切る（正しく動く） |
| `count` | 65,535 | 実用上あたらない |

**形式が直接縛るのは「各グリフの開始オフセット」であって、ビットマップの総バイト数ではない。**
最後のグリフがオフセット 65,000 から始まって 1,000 バイト消費する場合、
総量は 66,000 バイトだが開始オフセットは表現できる。

区別して読むこと。

| | 制約 |
| --- | --- |
| **形式上** | 各グリフの開始オフセットが 65,535 以下 |
| **v1 生成器** | 可変ピッチのビットマップ**総量**を 65,535 バイト以下に制限する |

後者は形式上の必然ではなく、**検証を単純かつ保守的にするための v1 の追加制約**である。

**どちらも可変ピッチだけの話。** 固定ピッチは先頭が `n * bytesPerGlyph` の算術なので上限がない。
実測（ビットマップのみ、刈り込み候補）:

| フォント | 字数 | ビットマップ |
| --- | --- | --- |
| DejaVu 72px（ASCII 95） | 95 | 37,361 B — 収まる |
| 日本語 12px（全文字） | 4,425 | 76,628 B — **溢れる** |
| 日本語 16px（全文字） | 4,425 | 125,884 B — **溢れる** |
| 日本語 16px（大きな集合） | 10,839 | 328,240 B — **溢れる** |

## 15. 適合性

### 15.1 適合データの不変条件

生成器はこれらを保証し、描画器はこれらを前提としてよい。

| 対象 | 不変条件 |
| --- | --- |
| `count` | `count >= 1`。**空のフォントは不正** |
| 連続索引 | `first + count <= 0x10000` |
| 疎索引の頭ブロック | `1 <= headCount < count`、`first + headCount <= 0x10000` |
| `codes` | 狭義単調増加（重複なし）。要素数は `count - headCount` |
| | 頭ブロックのコードを含まない。**`first` より小さいコードを含んでよい** |
| `glyphs` | 可変ピッチのとき非 `NULL`、要素数は `count` |
| | 固定ピッチのとき `NULL` |
| `bitmap` | 長さは固定ピッチで `count * bytesPerGlyph`、可変ピッチで `Σ ceil(glyphs[i].width * height / 8)` |
| | 上の長さが 0（全グリフ `width == 0`）のときに限り `NULL` を許す |
| `glyphs[i].offset` | **`i` より前のグリフのバイト数の合計に等しい**（累積オフセット） |
| `next` | 連鎖は**循環してはならない**。収録集合は重ならない |
| `height` | `height >= 1` |
| `yAdvance` | `yAdvance >= 1`（連鎖全体で一致、§8） |
| `xAdvance` | 0 でよい |
| `bytesPerGlyph` | 固定ピッチのとき `ceil(width * height / 8)` に等しく、255 以下 |

長さ 0 の配列は標準 C に無いので、`bitmap` が空になる場合は `NULL` を出す
（ダミー 1 バイトを出さない）。

**累積オフセットは正準出力（§10.4）だけの規則ではなく、全適合データの条件とする。**
グリフ間でのビットマップ共有や逆順配置は認めない。検証が単純になり、
描画器は `offset` を信用してよい。

ただし**描画器は `offset[i+1] - offset[i]` でグリフのバイト数を求めてはならない。**
バイト数は `ceil(width * height / 8)` から求めること。
将来この条件を緩めても描画器が壊れないようにするため。

### 15.2 描画器の義務

**描画器は次を満たすこと。**

- `codes` / `glyphs` / `next` の 3 つの `NULL` 判定すべてを扱う
- **固定ピッチのオフセット計算を 32bit で行う。**
  `uint16_t count * uint8_t bytesPerGlyph` を 16bit で計算すると大きな集合で壊れる
- 未収録コードでは `next` を辿り、連鎖の終端まで見てから未収録と判断する
- **未収録の描画は §7 に従う**（U+FFFD があれば描く、無ければ何も描かず送り 0）。
  独自の既定を持たない
- **U+FFFD への退避は、最も外側の連鎖を引き終えてから行う。**
  CellFont の `next` のさらに外側に別形式のフォントを繋ぐ実装（形式をまたぐ連鎖）では、
  **CellFont のデコーダの中に退避を置いてはならない。** CellFont 側に U+FFFD があるだけで、
  後段の別形式フォントに載っている字へ到達できなくなる。§7.2 が警告しているのと
  同じ事故が 1 段上で起きる。CellFont のデコーダは「見つかった／見つからない」を返すに留め、
  **退避の判断はフォント全体の連鎖を持つ側が行う**
- 連鎖の `yAdvance` は先頭のフォントのものを使う
- `width = 0` のグリフを、ビットマップを読まずに送り幅ぶんだけ進めて処理する
- **すべての読み出しを `CELLFONT_READ_*` 経由で行う**（§12.1）。
  `codes` / `glyphs` / `next` の `NULL` 判定も読み出した値に対して行う
- **索引の算術を 16bit 環境で安全に書く**（§7.1 の減算形）。
  `first + count` や `lo + hi` をそのまま書かない
- グリフ番号を `int` で返さない（65,534 まで取りうる）
- `<CellFont.h>` として §12.1 の名前を提供する

### 15.3 生成器の義務

**生成器は次を満たすこと。**

- §10 のエンコーダ規範に従う
- **可変ピッチでビットマップが 65,535 バイトを超えたらエラーで落とす。**
  黙って上位を捨ててはならない
- 収録コードが U+FFFF を超えたらエラーで落とす
- `codes` が狭義単調増加であること（重複が無いこと）を検証する
- 未使用フィールドに 0 を入れる（§3）
- 連鎖を出すとき、収録集合が重ならないこと、`yAdvance` が一致することを保証する
- §15.1 の不変条件をすべて検証する（特に連鎖が循環しないこと）
- **正規化後に §14 の全フィールドが範囲に収まることを検証し、収まらなければエラーにする。**
  入力の左端や縦の広がり次第で、正規化後の `width` / `height` が 255 を超えたり
  `xOffset` / `yOffset` が `int8_t` の範囲を外れたりしうる
- コードポイントが重複していたらエラーにする
- **`count` は出力 `CellFont` ごとに数える。** ある候補で 1 本でも `count > 65535` に
  なるなら、その候補は**表現不可として捨てる**（§10.1）。表現可能な候補が 1 つも
  無いときにエラーにする。`codes` が `uint16_t` なので入力は最大 65,536 字（BMP 全体）で、
  **それが 1 つの幅クラスに集まった場合だけ表現できない**
- 固定ピッチを選ぶ前に `ceil(width * height / 8) <= 255` を確認する（§10.3）
- §10.4 のタイブレーク規則に従い、同じ入力から常に同じバイト列を出す
- §12.2 の版ガード・`#pragma once` と §12.3 の命名規則に従ったヘッダを出す

## 16. 採らなかったもの

| 案 | なぜ採らなかったか |
| --- | --- |
| **グリフごとの bbox** | §13.1。H ≤ 12 では**増える**。16px 以上では効くが、そこは対象外 |
| **圧縮** | §13.2。16px で 1.5% しか縮まない。デコーダのバイト数に見合わない |
| **幅クラス表**（1〜2bit/字 + クラス記述子） | 刈り込めなくなる損が表の得を食い、16px 以上で負ける。**§10.2 の連鎖のほうが安くて強い**（形式の変更が要らない） |
| **コードの再マップ**（連番へ振り直す） | 疎索引比で 9% しか縮まないうえ、**文字列リテラルがそのまま使えなくなる** |
| **範囲表**（`{start, end, base}` の配列） | 6 バイト/範囲。実際の文字集合は散らばった 1 字が主なので、2 バイト/字のコード表より高くつく |
| **32bit オフセット** | 16bit で 64KB。超えるものは対象機に載らない。§15 のガードで足りる |
| **`codes` の 32bit 化**（追加面の対応） | 全フォントのコード表が 2 倍になる。必要なら別の形として足す |
| **構造体の version フィールド** | 焼き込み形式なので §12.2 の `#error` で同じ安全性が **0 バイト**で得られる。フィールドにすると 28 → 32 バイト |
| **オフセットの分割 2 バイト**（`offsetLo` / `offsetHi`） | `uint16_t` と同じ 4 バイトなのに、描画のたびにシフトと OR が要る。AVR でも `pgm_read_word` 1 回が 2 回になる。バイト順非依存の利点はバイナリ容器のためだが、容器は対象外 |
| **フォールバック用メトリクス**（豆腐の箱の寸法） | §7 の U+FFFD 規約で **0 バイト**。しかも豆腐を出すかどうかが文字集合の選択として表に出る |
| **`next` を描画器の API で持つ** | 4 バイト浮くが、生成ヘッダが描画器ごとの繋ぎ方を要求することになり可搬でなくなる（§8） |
| **バイナリ容器**（実行時読み込み） | 用途が対象機と食い違う。ファイルシステムを持つ機械は、字数が多ければ他形式のほうが小さい領域（§13）。magic `CEL1` のみ予約 |
